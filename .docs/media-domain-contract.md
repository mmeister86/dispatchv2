## Authority and immutable bytes

`media/r2.prepare` authenticates workspace membership, then an internal workspace mutation checks Owner/Admin/Editor, alt (1–1000 characters), declared format/size and quota before reserving an asset/session. Workspace reservations include in-flight/deleting assets: 512 MiB and 500 live assets. Legacy counters initialize from at most501 rows and fail closed if migration is needed. Retries with the same request UUID reuse the same session and do not double-reserve. Browser input never contains a bucket, object key, checksum, dimensions or ready state.

A ten-minute PUT grant covers only `temporary/<workspaceId>/<assetId>`; Content-Type and Content-Length are signed. Browser HTTP stacks set Content-Length themselves. Signature inspection is covered synthetically; actual R2 enforcement (wrong/extra/missing length), browser behavior, CORS and interrupted large transfers need live verification. CORS controls browser origins, not authorization/quota or actual file validation. Single bounded PUTs are used; no multipart sessions exist to abort.

`finish(sessionId)` atomically claims the session, increments a generation and fixes `final/<workspaceId>/<assetId>` before storage work. Only the backend conditionally writes that final key with `IfNoneMatch: '*'`; a browser PUT is never signed for it. It first reads an existing final object on resume. Otherwise it GETs and validates bounded temporary bytes, conditionally PUTs them and GETs the actual final bytes for validation again. SHA-256 is computed from final bytes, never from ETag/client metadata. Interrupted external work/DB commit retains the fixed key; an expired eleven-minute claim can be resumed. Duplicate active claims fail visibly; completed sessions return the same asset. Transport failures retain the claim; content failures become failed. Abandoned validating sessions have a24h resume window.

Every R2 read independently caps streamed bytes and verifies ContentLength against received bytes. No Convex `_storage` holds media bytes. Only internal `complete` may set ready, matching session size/type and generation. Workspace deleting/deleted or asset deleting blocks finalization, new version references and all publisher preflight/checkSend paths (including text-only content). Existing workspaces default active through optional lifecycle fields.

## Supported product/runtime limits

- JPEG/PNG: at most5 MiB, 4096 pixels per axis and8 million pixels. JPEG fully decodes with strict parsing,8MP/128MiB decoder limits. PNG preflights the sole 13-byte first IHDR, legal depth/color/compression/filter fields, bounded single palette/transparency/gamma chunks, contiguous image data and terminal empty IEND before CRC validation and decoding on the bounded non-interlaced path; interlaced PNG and APNG are explicitly unsupported because that decoder's interlaced inflate is unbounded.
- GIF: at most15 MiB,1 million canvas pixels,300 frames and30 million frame/canvas pixels. The library parses the frame structure; an additional strict bounded LZW check rejects the decoder's otherwise tolerated truncated/overlong streams. Final SHA includes every frame.
- MP4: at most32 MiB, one H.264/AVC video track plus optional AAC-LC audio, nonfragmented,0.5–140 seconds,1920×1080 or1080×1920 and<=60 average frames/sec. A bounded nested/table scan runs before MP4Box allocation: depth8,10000 boxes, one `moov`, at most2 tracks,20000 samples across the whole file and100000 counted sample-table entries. `sdtp` counts its four allocated arrays and is independently capped at20000 entries; duplicate structural tables and combined `stco`/`co64` are rejected before parsing. Sample offsets/sizes must fall within complete `mdat` bytes, and AVC NAL lengths/headers are checked. This validates container/codec/sample structure; it is not a video decoder/transcoder or proof of X processing success. Unlisted boxes/codecs can be rejected. These are conservative Dispatch Node-runtime limits, not current X provider hardcaps. Provider media IDs, asynchronous processing/status polling and expiration belong to the later publisher unit, whose publishing capability remains disabled until verified.

The supported MP4 data-reference form is deliberately narrow: `dref` version0, one exact12-byte self-contained `url ` entry with flags1 and no external payload; sample entries use reference index1 and audio version0. Sample-entry child levels count toward the same depth/box budget. AAC-LC `esds` accepts the fixed four-descriptor tree only, bounded length fields,2–64-byte AudioSpecificConfig and SLConfig2; ISO `meta` requires its full header. These checks run before MP4Box can recursively parse descriptors. Small malformed-entry regressions and a valid synthetic H.264/AAC clip cover this subset; no broader codec/container support is advertised.

## Content references and UI

New immutable versions atomically insert `mediaVersionReferences` by asset/version and capture final key/checksum. Deletion checks the indexed whole-history reference set, independent of latest100 resources/history UI. New assets are tracked from creation; legacy assets without an uploadSessionId cannot be deleted until an explicit historical reference migration. No automatic retrospective rewrite runs.

Library alt edits change only `defaultAlt`. Composer saves explicit per-version alt; changing it creates a new version, and existing schedules retain the old version/bytes/alt. GIF/video attachment is exclusive to one medium; static images follow the confirmed target account limits. Replacement requires the existing explicit new-version approval/schedule exchange flow. Loaded draft bundles and every historical version page include only workspace-authorized asset descriptors needed by their returned versions, so preview and exact-alt restore also work for old pinned assets outside the first100 ready-resource rows. The Composer and media library use the same authorized inventory query with50-row pages and explicit load-more controls; newest unreferenced uploads are available for first attachment.

Cloud UI uses XHR direct file PUT with actual upload progress and AbortController/XHR abort; prepare/transfer/finalize are awaited. Cancellation marks deletion and prevents a concurrent finalize commit. It never runs FileReader/dataURL/timer upload or studio rendering. Those simulations remain only inside the explicit VITE_DEMO_MODE=true component. Studio, transcription and clip rendering are honestly unavailable in cloud mode.

The MediaLibrary command guard resets its mounted state on each effect setup, including React StrictMode's setup/cleanup/setup cycle. True unmount or a keyed workspace change suppresses stale response feedback. `pnpm test:media-lifecycle` exercises the actual component with deferred local provider responses for success, failure, unmount and workspace replacement; it is UI lifecycle evidence, not a live storage test.

The native uploader input remains mounted after selection, preserving its visible filename and buffered File through errors. Accepted completion clears only the same submitted buffer; a newly selected File survives an older completion. `pnpm test:media-upload` exercises these actual browser cases with local deferred responses.

Private previews authorize current workspace membership/readiness for each120-second signed GET and refresh ten seconds before expiry; errors expose renewal. URLs remain in component memory, never draft/version/database/event storage. The paginated library bounds mounted previews; all requests ignore stale responses after unmount/workspace switch. A presigned GET already issued can remain usable until its short expiry after permission revocation/deletion.

## Cleanup, inventory and retention

New tables: `mediaUploadSessions` (workspace, asset, current uploader/request ID, server bucket/temp/final keys, optional normalized non-secret `r2AccountId`, expected format/size, grant expiry, state, claim generation/lease, next cleanup, optional deletion/error receipt); `mediaVersionReferences` (workspace/asset/version). New media metadata: optional uploadSessionId, server bucket and `r2AccountId`, MIME, width/height/duration, defaultAlt, errorCode; lifecycle gains uploading/validating/deleting. New workspace fields: optional lifecycle, mediaReservedBytes, mediaAssetCount. These are part of later export, coordinated workspace/user deletion and recovery inventory (TASK-36); include database references and R2 objects, not signed URLs/secrets.

Every new session and asset persists the physical namespace as normalized32-hex account ID plus bucket. Preparation replay/signing, claim/completion, preview, cleanup claim and receipt compare both bindings before storage effects or quota release. Same-namespace access-key rotation remains valid; credentials are not part of this identity. Missing legacy bindings fail closed with `MEDIA_BINDING_RECONCILIATION_REQUIRED` and visible manual reconciliation guidance, without automatic backfill. Cleanup defers unknown/drifted namespaces for24h while preserving asset state and quota; technical tombstones retain their namespace binding.

The15-minute Convex cron schedules bounded cleanup of20 due sessions. Final deletion waits beyond the full11-minute action lease and live PUT grant expiry+60sec. Delete calls are limited to10sec each so the worst bounded page remains under the action runtime. Failed external deletion has no receipt, keeps metadata/quota and retries after15min. Quota releases exactly once after final deletion receipt; referenced finals never get deleted.

A PUT may start before grant expiry and finish much later. Therefore technical deleted-session tombstones are retained and temp/final deletion repeats daily; ready-session cleanup also repeats temp deletion daily. One deletion at expiry would be insufficient. Deleted asset metadata drops filename, alt, checksum, MIME/dimensions/duration/error; deleted-session metadata drops uploader/request ID/error, retaining only the technical keys/IDs/limits needed for cleanup. Capacity ceiling is20 sessions/15min; upgrade sweep throughput or purge only after a verified native temporary-prefix bucket lifecycle rule and the later explicit retention policy. No native bucket lifecycle rule was created or claimed by this unit. Bucket config changes fail closed for old-bound sessions until an explicit migration/reconciliation.
