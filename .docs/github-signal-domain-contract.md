## Exact ingress and truthful acknowledgement

POST `/integrations/github/webhook` is on the Convex HTTP origin, not the `.convex.cloud` query endpoint. Configure the GitHub App webhook with this HTTPS route, the same `GITHUB_WEBHOOK_SECRET` (16..8192 characters), minimal subscriptions Push and Release plus the App's automatic authorization/installation events. `GITHUB_APP_ID` must match full installation security payloads. Recovery additionally requires the existing App client ID and RSA private key; no user/installation/PAT token substitutes for App-JWT hook APIs. Secrets are never entered into UI or copied to DTOs, logs or client bundles. Only setup key names are visible.

The default-runtime HTTP action reads unchanged raw streamed bytes, with an actual 256KiB bound and four-second read deadline independent of Content-Length. Native WebCrypto HMAC SHA256 validates a strict 64-hex signature before JSON parsing or any domain write. JSON must decode valid UTF8. Event/body discriminators reject altered headers that reinterpret Push/Release/repository/alert bodies as authorization revocation. Full installation events require matching signed App ID and concrete installation/account/target/permissions/selection shape; App-user revoked has action/sender and no installation. Push permits nullable head_commit and at most2048 supplied commits, retaining only the count/ref/SHAs/flags. Published Release must be non-draft and has actual ID/tag/prerelease/published_at. Unsupported supported-family non-published release/added/unsuspend actions return204 without enabling anything. Malformed/invalid signature writes no domain data.

A 202 is returned only after an atomic minimal sanitized receipt, GUID mapping, any immediate revocation barrier and native scheduled processor commit. There are no provider/model reads in that acknowledgement. The receipt RPC is bounded by an overall8.5-second acceptance budget; if it expires,503 represents an uncertain local commit, and subsequent signed provider retry can safely deduplicate. The deployment may still commit that in-flight mutation; 503 does not claim absence. Full raw payloads, commit messages/file arrays/diffs/release body and credentials are never durable journal copies. Provider costs remain unavailable rather than zero.

## Dedupe, fanout and authority

Technical body SHA256 is global; GUID maps the actual delivery to that body. Same GUID/different body or changed typed facts conflicts rather than overwrites. An identical factual body under another GUID shares the receipt. Separately signed reserializations of the same factual event deduplicate per workspace by stable Push installation/repository/ref/before/after/flags identity, or Release installation/repository/ID/published_at. No global event check suppresses another tenant. Native indexed pagination handles25 source rows per transaction; signal write and cursor/checkpoint commit together. Scheduled duplicates/crashes repeat safely. A one-minute cron re-enqueues at most20 overdue pending receipts and moves their retry deadline. There is no separate queue engine or unbounded table scan.

Source gates reuse TASK14 checkSource: active workspace lifecycle, current Owner/Admin authorizer and purpose actor, exact source generation, selected/access/monitoring purpose, accessible installation, matching connection generation and unexpired15-minute human repository proof. Source privacy/name must match the signed facts. Automatic admission requires a concrete purposeSequence strictly before the factual event admissionSequence; neither purposeAt nor receivedAt supplies authorization ordering. Both enqueue processing and commit occur within the same guarded mutation. Content=false still permits explicitly authorized factual monitoring but creates no content/model job. Historical retained tenant facts are not current source permission or model authorization.

Revocation barriers are durable before acknowledgement, so deferred20-connection/25-source batches cannot leave an authorization gap. Verified immutable GitHub user ID scopes revoked user grants even without installation; installation deleted/suspend closes its proof, actual repository removals close named source proofs, and empty all-to-selected removal conservatively closes installation proofs. Added/unsuspend/new permissions never restores local purposes. Source records/provenance remain; no deletion of derived drafts or remote uninstall is claimed.

The App has one native monotone revocation fence. OAuth states and discovery capture its sequence before provider I/O; completion compares applicable User/Installation/Repository barriers against that captured sequence. Background source guards compare authorized/verified sequences. This blocks late pre-revocation callback/discovery/refresh effects while allowing a genuinely new explicit human OAuth/resync/reselection afterward. New optional sequence fields keep preexisting TASK14 rows compatible and treat their baseline as zero. Fresh selection still has monitoring/content off.

A separate concrete native admission counter orders actual human configuration/reselection and the first factual receipt in committed mutations. Same-millisecond transactions and clock rollback therefore cannot authorize a pre-grant receipt. Same-body/GUID aliases retain their receipt; signed different-byte copies with the same factual eventKey inherit its first admissionSequence, including an unknown legacy value. Both actual purpose writers (configure and selection verification) record purposeSequence. The current source/proof/generation guards still run at admission, and explicit current Owner/Admin local recovery can independently admit bounded signed facts with original timestamps and explicit provenance. Older source or receipt rows lacking these optional fields remain automatically unentitled; no timestamp backfill or fabricated chronology is used. The Signals UI explains the required explicit local recovery. This singleton causes App-wide OCC contention for first factual events and purpose writes; split by installation only if measured throughput requires it. Security revocation sequencing remains independent, and factual revocationSequence stays zero.

Security bodies lack a signed occurrence ID/time: a byte-identical revoked body with a NEW GUID can be either a legitimate later revoke or an attacker replaying a previously signed body with an unsigned header. Known GUID redelivery is idempotent. An unknown GUID on the same security body conservatively advances barriers again, marks ambiguousRevocation, and visibly requires new authorization/recheck. It does not claim perfect replay immunity or trustworthy event ordering. At most100 aliases are retained per body; further unknown factual aliases conflict, while unknown security aliases beyond that storage ceiling still close authority again. Such unknown aliases cannot provide exact replay idempotence beyond that cap. Original receivedAt is retained; latestReceivedAt means a local receipt attempt, never original provider occurrence time. A repeated known GUID does not close a newer human grant again.

## Own failed-receiver detection and explicit redelivery

There is no user/installation-token fallback, arbitrary URL fetch or private detail GET. Each native continuation makes one15-second/no-retry/redirect-reject/1MiB-bounded provider read; an overall scan examines at most10pages/1000 attempts within two minutes and24hours. A capped/expired continuation stays visibly limited until a later scheduled window; it never silently resets into an infinite continuation loop. Successful complete scans have a global60-second minimum interval; cap/backoff blocks new requests until its recorded deadline. Rate headers drive bounded backoff, including403 exhaustion/Retry-After. Missing keys produce configuration evidence without a provider request.

The scan examines all delivery statuses, including null/0/no response and provider-success-without-a-local-signal, because the provider failure filter excludes some outages. JWT delivery installation/repository IDs must match current selected source proof before per-tenant recovery metadata is created. Duplicate attempt IDs with the same GUID group into one workspace recovery row. Native scoped25-source continuations are resumable and atomic. Global delivery inventory is never sent to a tenant. Checked time, oldest encountered permitted event attempt, finite window/cap and interruption/error are visible; unknown retention, over-limit bodies and older/missing provider inventory remain explicit gaps. Listing completion is not an assertion that all historical events were delivered.

Explicit Owner/Admin recovery validates active UI workspace and current role before claim and immediately before POST, plus current source/purpose/proof/generation. A deliberate new recovery command passes its currently displayed expected source generation and must still match the original JWT-observed installation/repository IDs; unknown/accepted polling never silently renews that authority. Cooldown and provider-attempt ceiling survive changed local purposes. No missing configuration consumes a lease. A60-second lease, monotone attempt sequence,15-minute minimum cooldown and max3 explicit provider attempts perGUID bound recovery across all entitled workspaces. Actual indexed same-GUID cooldown and cumulative attempt number prevent two tenant commands racing into duplicate POSTs; no tenant identity or private global inventory is exposed. Fixed `POST /app/hook/deliveries/{numericId}/attempts` must return202. No automatic POST retry occurs after an unknown transport outcome. 202 means accepted awaiting signed callback, not healthy/processed. The same actual raw-byte signed ingress must create a tenant signal before processed status. Timeout/lease expiry stays unknown, and source revocation during I/O cannot confirm authority for a new effect. Callback evidence before or after the provider response cannot be downgraded by a late unknown outcome. An existing signed factual receipt, including one previously blocked by expired proof or a then-disabled purpose, can be admitted by an explicit current Owner/Admin local-recovery command. Current actor/role/workspace/lifecycle/source generation/monitoring proof and signed installation/repository/visibility/name must match in the same transaction. This is a new human authorization for bounded facts, not a retroactive entitlement claim: original receivedAt/providerAt stay unchanged and optional explicitRecovery records actorId/authorizedAt/recoveryId alongside current source generation. A sequence increment and atomic event-key dedupe fence repeat clicks and late remote finishes; no provider POST, cooldown reset or attempt increment occurs. Ordinary background processing retains the original factual admissionSequence bound and never silently binds to fresh authority. The UI distinguishes local signed-fact admission from remote202 acceptance. Unsupported or drifted identities remain closed.
