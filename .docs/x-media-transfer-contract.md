# R2-to-X media preparation — TASK-12.1

This unit supplies the internal media engine behind the existing authorized publishing schedule. It does not send posts or activate the engine from `publishing.dispatch`, which still reports publisher unavailable. TASK-12.2 owns explicit first-write consent/evidence and post sending. Scope eligibility or configured key names do not prove provider entitlement. All publishing/approval guards remain in force; current unverified accounts remain disabled. Tests use explicitly synthetic verified accounts.

## Exact source and credentials

`publishing/media.approvedSource` derives workspace, account, approved version, source and exact historical alt solely from schedule ID, generation and media position. It runs the reviewed scheduler/approval/account-connection checks and requires an X account, version-to-draft identity, content-reference-to-snapshot correspondence, workspace-authorized ready asset and completed reciprocal upload session. Final key must equal `final/<workspace>/<asset>`, session fixed final key and snapshot key; saved SHA-256, size and MIME must agree. Both records must retain the configured normalized R2 account and bucket. Missing legacy session/bindings, deleted/unready assets, drift and foreign references fail closed. Library default alt is never substituted.

The Node action uses the existing EU-only R2 client and bounded final-only GET, with fresh SDK configuration on each invocation. It never calls upload finalization, creates an approved final from temporary bytes or stores a signed URL. Actual received bytes pass the existing bounded format validator and full approved SHA-256 before initialization or append. Every append action reads/validates the complete object again before selecting its segment. This deliberately trades additional bounded GETs for safe resumability without persisted binary payloads or a second storage client.

Each external X request obtains `client.credentialForSchedule(operation=media)` and the last database gate rechecks exact source, scheduler/approval/lifecycle, current connection/scopes and credential generation through TASK-10's `scheduleSource`. Database checks cannot eliminate revocation in the interval before a network request; late confirmed outcomes are recorded but subsequent calls are blocked.

## Checkpoints and bounded execution

`xMediaCheckpoints` has one row per schedule generation/media position/upload attempt. Stored identity also pins version/account/source key/checksum/alt, and mismatches cannot reuse its mutable X media ID. The indexed lookup takes at most four rows and enforces three total preparation attempts. Expired known IDs can start a fresh bounded attempt; unknown write outcomes cannot. Each attempt has a thirty-minute wall-clock processing budget, at most thirty status reads, an eleven-minute action lease and monotonic claim sequence. Each action handles one phase with a fifteen-second X request timeout; the existing R2 read timeout is thirty seconds. Processing sleeps are native scheduled actions, never long Node sleeps. Watchdog callbacks recover interrupted read-only work and mark interrupted writes uncertain.

Initialization saves the returned ID and expiry. Append uses native multipart `media` plus `segment_index` 0–999, segments at most4MiB. Successful validated append receipts increment confirmed segment/bytes/chunk count; confirmed chunks are never repeated. Finalization and status parse bounded IDs, finite expiration and known processing states. Processing failure is permanent; pending/in-progress saves provider wait time and schedules a later status action. Safe read-only status failures use bounded backoff and Retry-After within the overall budget. A provider media ID must have at least sixty seconds remaining before another effect or future attach; `ready` rechecks authorization and current credentials before returning it.

Before every external phase, operation intent/claim/generation are durable. Unknown initialize/append/finalize/metadata outcomes pause as `uncertain`; there is no automatic write retry, workflow retry or SDK retry. HTTP rejection is separate from uncertain transport/invalid acknowledgement. Metadata is exactly `{id, metadata:{alt_text:{text: approvedAlt}}}` to `POST /2/media/metadata`. Its bounded response must acknowledge the same ID before `metadataApplied` and `ready`; failure never silently drops alt. Receipts preserve known external outcomes after cancellation/revocation and prevent stale claims from advancing current state.

## Measurements and inventory

Per-attempt metrics retain received R2 bytes (including partial failed reads), acknowledged X media bytes, submitted media payload bytes (possible transmission, not confirmed receipt), acknowledged chunks, selected X requests, cumulative action phase duration and incomplete-measurement flag. Missing/crashed acknowledgements can have costs even with zero confirmed bytes. `measurements` is a membership-authorized secret-free projection with no alt, object key, token or URL. It returns a payload-only reference estimate in USD (`bytesSubmitted / 1e9 *0.12`, `convex-pro-us-east-2026-10-05`) and `billedUsd:null`. The reference rate is the [published Professional US East egress price](https://www.convex.dev/pricing), read2026-10-05. This is neither a billing receipt nor an estimate of complete action/DB/R2/X cost: actual plan/region/allowances, request/response overhead, compute and X usage remain unknown. R2's own egress policy never means Convex transfer is free.

New table indexes: `by_scheduleId_and_generation_and_mediaPosition` and `by_workspaceId`. Checkpoint records include workspace/schedule/version/account/asset identifiers, approved alt and technical source bindings; keep them in the later TASK-33/36 export/deletion/restore inventory. No tokens, raw media bytes, provider response bodies or signed URLs are stored. There are no new configuration keys, dependencies, public provider-write APIs or UI changes. Lifecycle guards stop future effects. Expiry is checked on every resume/ready lookup; checkpoint rows and IDs are retained for later publication evidence/reconciliation rather than purged by a speculative retention policy. The current action lease/watchdog is transient-work cleanup, not deletion of approved R2 bytes or a guarantee of remote X deletion. TASK-33/36 must apply the approved retention/deletion policy without erasing publication evidence.

## Evidence and live gates

Synthetic targeted checks cover exact source/alt, foreign and missing reciprocal session, snapshot mismatch, namespace drift, stale generation, revoked approval, role/lifecycle loss, actual wrong-checksum final read before X effects, confirmed phase resumption, processing wait/failure and status retry budget, interrupted reads versus uncertain writes, expired ready restart, metadata rejection, credential scope loss after source retrieval and cancellation with a late initialized ID. Existing media byte tests cover bounded JPEG/GIF/H.264/AAC formats and stream size validation. X transport tests check fixed HTTPS/redirect refusal, bounded response parsing and nested alt response IDs. They are runnable without live credentials or provider writes.

The conservative prior product caps remain JPEG/PNG5MiB, GIF15MiB and MP432MiB with the media contract's decoder/container limits. Retrieval accumulates a full bounded Buffer; it is not zero-copy. With one complete read per append, a32MiB video can read288MiB across initialization and eight chunks, plus bounded decoder/copy allocations. An action never persists those bytes. Synthetic durations are not proof of configured Node RSS/runtime/egress for maximum assets: real EU R2 jurisdiction/access/CORS, actual bounded runtime and measured costs, real X upload/processing/alt/attach entitlement and explicit human-approved test account/content remain manual acceptance gates. No actual OAuth, X upload/post, R2 object mutation, email or bucket creation occurred in this unit.
