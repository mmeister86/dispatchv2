## Authority, one-use callback and identity

`integrations/x/client.start` authorizes the verified Better Auth session through the existing workspace wrapper; Owner/Admin and the domain user's current `activeWorkspaceId` are required. It generates cryptographic random state/verifier, S256 PKCE and a ten-minute state record. The state digest is indexed; the verifier is encrypted with workspace/digest association. A fresh attempt replaces the same initiator/workspace's prior attempts, including a claimed callback. The browser never receives the verifier.

The registered redirect is exactly `SITE_URL/integrations/x/callback`, derived from a validated server URL. HTTPS is required except localhost/127.0.0.1 development; userinfo, query, fragment and path prefixes are rejected. There are no client-controlled provider endpoints, redirect URIs, user IDs, memberships or provider identities. OAuth2 confidential client ID/secret are distinct from Consumer keys and application-only bearer tokens.

The authenticated callback uses the normal ProtectedRoute/AuthBoundary/WorkspaceStoreProvider, preserving its destination through the existing login return path. Its action reauthorizes before claiming state and again at each commit. Wrong initiator, workspace, role, current selection, lifecycle, expiry or replay fails; wrong attempts do not consume someone else's valid state. Claim removes the verifier from the DB before exchange. A provider denial consumes only the matching valid state and performs no exchange. Interrupted exchange cannot retry a consumed code; reconnect is explicit.

The actual `/2/users/me` numeric ID owns identity; editable handle/name are display data. Same-identity reconnect in the same workspace preserves the social account ID and historical approval targets. A different identity cannot replace that ID; connect a separate account. Indexed global `xBindings` serialize concurrent completions, including accounts requiring reauthorization. Existing legacy connected/reauth account rows also reserve identity. Only explicit authorized disconnect releases a binding, followed by fresh OAuth in the new workspace. Conflict errors reveal no foreign workspace/account details.

A transactional singleton OAuth counter orders starts, bindings and disconnects. Binding changes after a fresh flow started invalidate that flow even if provider identity was not yet known. Reconnect also checks the captured credential generation. This avoids wall-clock races, including Convex's fractional document creation timestamps. The singleton is a deliberate small-connect-volume limit; replace only after measured contention, while retaining serializable transfer ordering. Legacy states lacking the sequence are rejected; optional fields permit safe deployment without claiming a migration.

## Credentials, rotation and refresh

`xCredentials` is server-only and separate from public `accountFields`. AES-256-GCM uses native WebCrypto, random 12-byte IVs, version1 envelope, named key and authenticated association `x-token:<workspaceId>:<accountId>`. PKCE uses a separate association. Strict canonical Base64 key material must decode to exactly32 bytes. There is no weak fallback or client key. Current key writes plus one previous key read permit gradual rotation through successful refresh/reconnect. Keep the previous key until all still-needed records have been renewed/reconnected; changing bytes under the same key ID is not key rotation and produces `X_CREDENTIAL_UNREADABLE`.

Unknown/unreadable key during refresh becomes visible `reauth_required` with a fixed actionable code and removes the unusable local credentials. Recovery is explicit fresh OAuth after valid encryption configuration; this does not claim a missing key can recover a destroyed credential. Initial PKCE decryption failure also fails the flow visibly. Database/envelope exports and server logs are secret-bearing operations; do not include these records in client DTOs or ordinary workspace exports.

Refresh is an authenticated Owner/Admin command. Its mutation claims a60-second lease and increments generation before the external token exchange. One parallel claimant wins; others receive `X_REFRESH_IN_PROGRESS`. Completion rechecks current user selection, role, membership, active lifecycle, account binding, connection and exact generation before atomically saving access/refresh tokens. Fresh OAuth and disconnect advance generation; a stale completion/failure cannot overwrite or resurrect newer credentials. Confirmed replacement refresh tokens are saved with their access tokens. A confirmed OAuth response without a replacement refresh token retains the original, per [RFC6749 §5.1/6](https://www.rfc-editor.org/rfc/rfc6749); an omitted refresh scope retains the original granted scopes. Initial exchange requires actual returned scope evidence. Response fields, bearer token type, token sizes, finite positive expiry and scope syntax are strictly bounded. The shared initial/refresh token validator accepts only printable ASCII without whitespace/control characters; malformed refreshed access or refresh tokens never persist or report success, and require reconnect because rotation outcome is unknown.

401/403 or `invalid_grant` disables the local credential and requires reauthorization. Transport, timeout, malformed or otherwise uncertain refresh outcome also disables it as `X_REFRESH_OUTCOME_UNKNOWN`; a potentially consumed rotating token is never blindly retried. An action crash leaves the durable lease: a subsequent claim or cleanup marks an expired lease unknown and removes secrets, preserving the global binding. There is no indefinite stuck refresh or automatic publishing retry. Refresh retains the OAuth connection sequence.

The future publisher's narrow internal `credentialForSchedule(scheduleId,generation,operation)` rechecks an in-flight exact schedule, scheduling actor authority, exact approval, connection sequence, current lifecycle, binding, connection, required text/media scope, no refresh lease and at least30 seconds token validity. It decrypts internally then rechecks generation before returning a token exclusively to server code. No arbitrary public credential read or publicly exported token getter exists. Expired credentials require the explicit authorized refresh/reconnect path; publisher/media orchestration is a later unit. A later external send still needs its immediate schedule/credential guard; a DB transaction cannot undo an HTTP request already in flight.

## Disconnect, planning and evidence

Disconnect immediately removes local ciphertext, increments credential generation, disables account publishing and releases its binding. Pending reconnects cannot commit through the old generation/order. Existing versions, approvals and history are retained. The operation reports local disconnection independently of remote revocation. No remote revoke call is attempted: there is no evidence that an old grant revoke cannot affect newly authorized same-identity credentials. Settings explicitly instructs provider-side connected-app removal if desired. A request already in flight may complete; local disconnect cannot prove the absence of an external effect. Later account/workspace deletion must not claim provider access was removed until an actual remote receipt or manual evidence exists.

Fresh OAuth writes a new non-secret `xEvidence.connectionSequence`. New schedules and explicit reschedules capture `accountConnectionSequence`; shared publishing preflight and internal credential access compare them. Old schedules, including legacy rows without that field on real OAuth accounts, fail closed after reconnect even if a later publisher proves live entitlement. Explicit human reschedule may retain the exact already-approved version/account under the existing domain rules. Token refresh retains the sequence and does not invalidate schedules. Legacy non-OAuth fixture accounts with neither sequence remain compatible; they have no X credential access path.

Public resources explicitly map permitted account metadata. `xEvidence` includes bounded scopes, verified identity time, connection sequence, separate text/media scope eligibility, live-write status and fixed sanitized error/revocation status. Initial/reconnected live-write status is `unverified` and `capability.publish=false`. Returned scopes and identity do not prove successful publishing, subscription entitlements, premium length, quotes, metrics or research access. Conservative local account limits are280 characters,25 thread positions and, only with media.write,4 media references plus existing validated image/video types (otherwise0/no media types); these are Dispatch caps, not claims about provider hard limits. A later publisher unit must provide actual entitlement/write evidence before enabling publishing. No publisher, upload or reconciliation was implemented here.

Until TASK-48 paginates the shared100-row account inventory, creation is limited to100 total retained accounts per workspace, including disconnected/history targets. Capacity failure is explicit, never connection success; reconnect existing IDs remains available. Legacy identity checks read at most101 indexed rows and fail closed beyond that bound. No account deletion or implicit historical target reassignment was added.

## UI lifecycle and browser handling

Cloud Settings uses actual awaited start/refresh/disconnect commands, persistent reactive connection state and role controls. Missing/invalid server config visibly disables connect/reconnect; key names and registered callback instructions contain no secret values. Demo account simulations remain in the explicit `VITE_DEMO_MODE=true` branch; the OAuth callback itself is unavailable in demo mode.

Callback buffers code/state only in component memory and cleans its browser query at effect setup. React.StrictMode's setup/cleanup/setup observes the same in-flight promise; it neither re-exchanges the one-use code nor suppresses the only completion handler. True unmount and workspace replacement ignore stale feedback; switching current workspace fails visibly without retrying the old code against a new workspace. Login may carry the callback destination until authentication; no code/state is written to localStorage, database events or logs by this unit. OAuth URLs should still be treated as sensitive browser history data.

Provider requests use only fixed HTTPS token/me endpoints, reject redirects, cap streamed response bytes at32KiB before JSON parsing and time out after15 seconds. Sanitized fixed error codes replace provider bodies. No user token/client-secret form is forwarded to arbitrary or redirected origins. There are no automatic non-idempotent external retries.

| --- | --- |
| `xOAuthStates` | workspace/initiator IDs, digest, encrypted optional verifier, fixed redirect, optional account/generation, start sequence, status and ten-minute expiry. Claim strips verifier immediately; every15 minutes delete at most50 expired rows. Fresh attempt deletes the bounded prior initiator/workspace rows. Keep out of exports. |
| `xCredentials` | workspace/account, generation, encrypted optional tokens, finite access expiry, granted scopes, lease and indexed next cleanup. Connected credentials remain until authorized disconnect/reconnect or later retention/deletion. Failed/disconnected rows retain only generation metadata, no ciphertext. Due leases/staged credential records are bounded50 per15-minute sweep and become reauth; technical generation tombstones remain so stale actions cannot revive access. Keep ciphertext out of workspace exports. |
| `xBindings` | provider ID and optional bound workspace/account, change timestamp and sequence. Disconnect releases references but retains ordering tombstone. Expired-state/lease cleanup never releases active identity binding. Later deletion must explicitly release only the matching bound account after disabling local use. |
| `xOAuthFence` | one non-secret global ordering counter (`key=oauth`); no account/user data; preserve for transfer ordering. |
| `socialAccounts.xEvidence` | public bounded capability evidence, fixed errors and remote-revocation status. No token, verifier, digest or raw provider response. Existing history remains targeted at the same ID. |
| `schedules.accountConnectionSequence` | optional compatibility-safe field capturing exact OAuth connection; reconnect invalidates old scheduled/in-flight access until explicit reschedule. |
