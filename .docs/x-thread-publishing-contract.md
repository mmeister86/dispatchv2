# Approved X thread publishing — TASK-12.2

This unit replaces the unavailable publisher with native Convex scheduler steps. It uses existing immutable `draftVersions`, human approvals, schedules, encrypted credentials and the TASK-12.1 media engine. TASK-12.3 owns read-only reconciliation and an explicitly confirmed continuation; neither is simulated here. No SDK, Workflow or Workpool retry wraps a post write.

## Ordered operations and outcomes

`publishing.dispatch` invokes the due schedule claim once. The same claim mutation commits `publishing` and durably registers the first `workflows.step`; dispatch performs no later action handoff. A crash after the claim returns cannot strand the initial job. Each `publishing.workflows.step` claims exactly the next unconfirmed position in `xPostAttempts`; the operation identifies workspace, schedule/generation, immutable version, account/provider identity, connection sequence, position and attempt. The text and approved media/alt snapshot are retained in the immutable version rather than duplicated into logs or every operation. A position records its exact previous confirmed external ID as the reply parent.

A preparing claim has an eleven-minute lease, outliving Convex's ten-minute action limit. Interrupted preparation can safely resume. Immediately before fetch, `attempts.beforeSend` checks current schedule state/generation, Owner/Admin scheduler and approver authority, approval/revocation/purpose, active workspace, draft/version/account relationships, connection sequence, reciprocal provider binding, actual current credential generation/scopes/lease/expiry, weighted text limits, pinned media source and provider media expiry. It atomically records `sending`, request start time, credential generation, exact attachment IDs and actual media keys. Actual optional keys are retained from initialize, finalize and status acknowledgements. A later missing key preserves prior evidence; a contradictory key for the same media ID stops preparation as `uncertain` with `X_MEDIA_KEY_CONFLICT`, retaining the original key and preventing attachment. Keys absent from every acknowledgement remain explicit `null`; no key prefix is inferred from a media ID.

One native fetch sends `POST https://api.x.com/2/tweets`, fixed HTTPS, redirects rejected, a fifteen-second deadline and a streamed response capped at 32 KiB. Body is `{text, media:{media_ids:[...]}, reply:{in_reply_to_tweet_id:...}}` with optional nested media/reply. Approved text is sent unchanged. Only status 201 and a numeric `data.id` confirm a post. The next call immediately persists that ID with compare-and-set on attempt/claim sequence, adds its canonical `https://x.com/i/web/status/<id>` result link and updates the confirmed count. Confirmed positions are skipped on resume: a worker stopping after positions 1 and 2 sends only 3 next. Actual IDs survive cancellation or connection changes; late outcomes never resume cancelled jobs or enable a newer connection.

A crashed `sending` lease, transport timeout, malformed/oversized success, non-201 success or POST 5xx has a possible external effect. It becomes `unknown` and the schedule becomes `reconciliation_required`; no automatic resend occurs. A valid 201 ID with partial provider errors is still checkpointed because the write happened. Narrow HTTP 400/401/403/422/429 rejection is recorded separately. Rejected operations stop as failed/partial without automatic retry; actual 401/403 closes the current standard publishing gate. Rate-limit reset and HTTP status are retained as bounded evidence. A response lost before persistence remains unknown even if X created the post.

The database guard and HTTP effect cannot be atomic. Revocation during an in-flight request can still leave a visible post; its actual receipt is stored while the next position is blocked. No exception class is treated as proof that a started fetch was unsent. Stale CAS receipts cannot overwrite confirmed positions. A confirmed late response for an unknown operation can supply its real ID, but does not automatically continue the stopped job.

## Abort intent and unresolved outcomes

Public `editorial.cancel` checks active workspace access, Owner/Admin role and schedule ownership before its idempotent return. The first valid abort stores optional `abortRequestedAt` and `abortRequestedBy`, cancels the original scheduled job and increments the schedule generation once. A repeated abort, including a retry with the original expected generation, returns without changing generation, state, actor/time, error or outcome evidence. An un-aborted stale generation still fails with `SCHEDULE_CONFLICT`.

Cancellation reads at most 101 attempts through the schedule prefix of `by_scheduleId_and_generation_and_position`, across retained generations. Publishing or existing reconciliation state, any `sending`/`unknown` attempt, or overflow beyond the 100-row cancellation bound remains `reconciliation_required`. Its existing error code and confirmed external IDs/count are retained. A definitely stopped prefix with only confirmed/rejected attempts may become `cancelled`, preserving successes. Scheduled work with no possible effect may also cancel. A claim without an attempt is treated conservatively as requiring reconciliation.

Schedule and position claims refuse persisted abort intent. The shared approval/send guard also refuses it, covering preflight, credentials and media attach even if a later state transition accidentally writes `scheduled` or `publishing`. Rescheduling an aborted job is forbidden. Existing account/state indexes therefore continue blocking another first-write proof while this job requires reconciliation. Old-generation callbacks may store their actual confirmed ID or unknown/rejected outcome, but cannot advance the job, activate write proof or clear the barrier. Watchdogs never resend an aborted position.

TASK-12.3 must provide a separately authorized Owner/Admin read-only reconciliation path for aborted jobs; the send guards are not relaxed for it. Only actual reconciliation may finalize an unresolved abort. An abort intent prevents continuation after reconciliation, and confirmed visible posts remain retained. These two optional audit fields belong to schedule export/deletion/restore inventory alongside the exact version, approval and attempt evidence. No new table or index is introduced for abort handling.

## Media placement and bounds

The product stores one ordered version-level media list. All approved media attach to the first post only; replies are text-only. Approval/confirmation clearly displays this decision and the historical exact alt text. Each attach uses TASK-12.1 `media.ready`, which rechecks the source, reciprocal ready R2 upload session, namespace/checksum, current credentials, acknowledged alt metadata and sixty-second provider expiry margin. Preparation runs through its existing bounded engine, never a second upload engine. Coordinator waits are ten-second native scheduler steps, bounded by a forty-five-minute overall publishing budget, without long action sleeps. Terminal failed/uncertain/blocked media stops the coordinator; it never drops media and sends text instead. Expired ready IDs can be prepared again only before the unsent first position. Confirmed posts are untouched.

## Concrete first-write consent

OAuth identity/scopes leave `capability.publish=false`. Normal approval, calendar creation and rescheduling retain the ordinary capability gate. A concrete `editorial.approveFirstWrite` command permits only current Owner/Admin human approval of the current exact version/account, eligible actual credentials/scopes and immutable media. It stores purpose `first_write_verification`, actor, exact connection sequence, media placement and forty-five-minute expiry. There is no public/model `allowUnverified` flag.

The separate `editorial.confirmFirstWrite` command verifies that same actor/version/account approval and creates an immediate persisted verification schedule with confirmation time and expiry. The Composer explicitly says it creates visible X content, shows every stored segment/media/alt and target handle, and requires a separate visible-post acknowledgement. Both commands are awaited; failure preserves local content and displays guidance. A remote revision invalidates the dialog and preserves dirty Composer buffers. Repeat confirmation returns the original job. Active scheduled/publishing/partial/unknown jobs for the same account block a second first-write job, including another draft. Verification approvals cannot authorize ordinary calendar jobs, and their immediate jobs cannot be moved into future slots.

Central approval, credential and media guards accept the exception only for the valid persisted purpose job. Every later position stays within its consented immutable snapshot/connection/expiry. Only an actual credentialed POST acknowledgement still bound to current connection and credential generation/scopes stores `xEvidence.writeProof` (actual post ID, attempt ID, confirmation time, sequence) and enables standard publishing. Unknown, stale-connection, cancelled or read-only candidate matches never enable capability. Premium text, quotes, research, metrics and other separately gated capabilities receive no proof from this standard post.

## Text validation

`shared/xText.ts` uses the official exact pinned `twitter-text@3.1.0` parser (types 3.1.10) in backend validation, approval/scheduling/send preflight and real Composer/model validation. CJK weights, recognized emoji sequences, detected URL length of 23 and internal NFC counting use `parseTweet`; malformed UTF-16 and invalid characters fail. An empty editing field can be saved, while approval/send require nonblank text. Standard X remains capped at 280 weighted characters. The original text, URLs, whitespace and decomposed Unicode are never rewritten in the approved snapshot or request.

Package inspection found the package's ESM entry exports a default object, so the shared import uses `twitterText.parseTweet`. Its published parser bundles through Convex and Vite and runs in the real Composer browser fixture. Its existing core-js 2 transitive dependency remains pinned; no dependency build scripts were approved or executed for it. Resolved production dependency audit found no known vulnerabilities; package age and future X parser changes still require explicit upgrades and regression checks.

## Inventory and user-visible results

New table `xPostAttempts`: indexes `by_scheduleId_and_generation_and_position` and `by_workspaceId`; fields include bound IDs/position/attempt, stages, claim/lease/deadline, credential generation, exact attachment IDs and actual nullable media keys, reply parent, external ID/status/rate-reset, error codes and timestamps/duration. Reads are indexed and capped at 101 rows against the 100-post product ceiling. It stores no token, raw response body, media bytes, signed URL or content journal copy.

Compatibility-safe optional fields: approval purpose/connection sequence/expiry/media placement; schedule abort actor/time, purpose/intent expiry/confirmation/media placement and bounded external post evidence; account `xEvidence.writeProof`; media checkpoint actual `mediaKey`. New schedule indexes `by_approvalId` and `by_workspaceId_and_accountId_and_state` support idempotent confirmation and the current account guard. No new configuration variables are required.

TASK-33/36 export/deletion/restore must include these records, exact version/media/approval links and provider outcomes. Outstanding effect receipts require retained schedule/attempt tombstones until reconciliation; an account or workspace deletion cannot erase evidence while an action is in flight. Lifecycle barriers stop new effects. No speculative automatic purge erases unknown or partial results. Account proof and media/post keys are non-secret outcome evidence, with tenant authorization on the ordinary workspace projection. Media transfer usage remains recorded by TASK-12.1; post attempts record durations and possible request starts. No synthetic zero billed cost is shown.

Composer and Calendar show immutable scheduled snapshots, real confirmed IDs/links/counts, partial/unknown/failed status and guidance. No timer/random success exists in the real flow. Reconciliation/explicit continuation remain visibly unavailable until TASK-12.3, rather than showing a fake success button.
