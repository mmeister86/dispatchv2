## Profiles and immutable configuration

One `researchProfiles` row exists per actual workspace/account, enforced by indexed transactional creation. Owner/Admin/Editor can create and edit this shared profile; Viewer can read it. Public commands use existing verified authentication, current membership, active workspace lifecycle and canonical same-workspace account/profile references. New profiles require manual frequency, an inactive schedule and null cap. No processing policy, pricing or budget grant is seeded.

Configuration includes bounded topics, project relation as untrusted human text, audience, languages, region preferences, up to ten preferred HTTPS source hints, exclusions, a 1–90 day freshness window, 1–20 topics, manual/daily/weekly frequency, IANA zone, local clock and weekly weekday. Regions, languages and source URLs express preferences, not provider support, permission or an arbitrary fetch capability. Automatic handoff is stored as false and unavailable.

Every explicit profile command appends an immutable `researchProfileVersions` configuration and receipt, checks expected revision CAS and advances the live profile revision. Actor-scoped command keys bind an exact fingerprint; acknowledged replay returns the original revision, contradictory payloads fail. Create replay returns its actual original profile ID; a second distinct creation cannot replace a profile. Deleted profiles remain tombstones; this unit provides no restore or silent recreation.

An optional cap is a positive safe integer of at most 1e12 micro-units in the actual currently approved generation pricing currency. Changing the cap requires that current pricing/purpose configuration. An unchanged historical cap can remain during ordinary profile edits after policy withdrawal, and removal is explicit. The real editor preserves currency/value and prevents automatic relabelling or conversion when current currency changes. Caps confer no budget or search approval.

## Explicit prepared schedules

D02 permits an explicitly activated **prepared** native schedule, visibly described as producing blocked order receipts. Activation checks the finite profile cap, connected account/connection sequence, current generation processing/pricing evidence and research purpose, and indexed provider/workspace/account grants with mandatory current Owner/Admin approvers for workspace/account (provider approvedBy is optional; a present approver is checked), matching version/currency/purpose/expiry, safe held/spent values and enough remaining coverage for the full cap. This is a read-only prerequisite check, not funding, consumption, reservation or native-search authority.

Activation pins actor, account sequence, exact policy version/full record fingerprint and the three actual grant IDs under `generation-prerequisites-only`. TASK21/22 must require explicit new activation capturing actual native X/Web provider processing, pricing, source permission and funding evidence. Deploying an adapter must never turn these prepared schedules or historical blocked orders into paid work.

Native `ctx.scheduler.runAt` saves the concrete UTC occurrence and native job ID transactionally. Clock planning reuses `src/lib/time.ts` civil-date and wall-time helpers: skip nonexistent local times; choose only the earlier occurrence in a DST overlap before testing whether it is future; daily/weekly recurrence uses the saved IANA zone and weekday. It plans strictly after current server time. A bounded 15-day search covers a skipped weekly DST occurrence. No client timezone, automatic missed-period batch or account preference change shifts a saved occurrence.

Save, pause/unpause, deactivate and delete cancel the old native job, advance schedule generation and clear activation. Reactivation is explicit. Pausing does not imply an unrelated financial refund or parent-chat stop. Callback authority rechecks current profile pause/tombstone, workspace, saved actor role, account connection sequence, current policy fingerprint and full grant coverage. Withdrawal stops the prepared schedule with a coarse persisted reason. Old generations, earlier duplicated delivery and future/mismatched timestamps cannot create another order. UTC instant plus generation identifies one occurrence even when replanning happens in the same millisecond.

## Unified orders and concurrency

Manual and scheduled callers use the same `admit` domain function and `researchOrders` store. The occasion validator also represents a later agent request; there is **no** public actor/run/currency hint and no new model tool advertised in TASK20. A future concrete Content-Agent caller must derive its current authorized conversation/run/operation and bounded human permission server-side before using this domain boundary. Existing chat tools continue to describe research as unavailable.

Each actual order pins workspace/account/profile, immutable profile version and copied bounded configuration, actor, connection sequence, occasion, exact command/occurrence identity, generation, search window and deadline, cap/currency and any concrete generation prerequisite receipt. The active profile pointer admits at most one queued/running order transactionally. Concurrent manual requests cannot create a queue. A scheduled occurrence overlapping an active order produces one terminal `RESEARCH_ORDER_ACTIVE` receipt, leaving the original active snapshot unchanged. No pending queue, second run store, Workflow, Workpool or financial ledger exists.

Occurrence receipts use the profile/occasion/operation-key index independently of the current schedule actor. Replay returns the historical actual receipt after terminal completion, pointer clearing, pause or replanning. Explicit later human requests use distinct command keys; a historical receipt is not a new attempt.

The current native executor checks live authority, the captured connection sequence/deadline and the order's own immutable configuration/prerequisite receipt, then records `blocked` with `RESEARCH_DOWNSTREAM_UNAVAILABLE` or the actual coarse configuration/authority reason. It never compares a job's captured version with the profile's mutable current version. Editing a profile therefore cannot mutate or invalidate that admitted job's snapshot. Pause/stop/delete/access withdrawal remain independent live fences.

Current Owner/Admin/Editor may stop a shared research order. Stop fences only this research order's generation and active pointer; it does not touch a parent personal conversation or its Agent execution. Delete cancels the profile schedule and active research shell, preserving immutable receipts. `usageMicros` is null, never a fabricated zero, and there is no completion, result count, last success or paid call in this unit. A later actual pipeline must connect TASK17's conservative holds and stable logical paid-step identity before any paid search attempt; the snapshot cap alone does not enforce search expenditure. Existing unknown/sent Agent liabilities and late settlement remain unchanged.

## Real UI and commands

`ResearchPage` branches explicitly into existing Demo and real Research. Real mode has no sample Inbox, seed completed run, fixed euro quota/cost, synthetic progress/confidence, fake timestamps, timers or local draft handoff. It shows actual saved native next invocation only, unavailable cost/last success and paginated real order receipts. Profile creation/editing remain useful without provider configuration. Inbox and handoff remain truthfully unavailable.

Commands await actual mutations and disable duplicate pending submission. One failed command retains its original closure and key behind a separately visible exact retry. The control remains available after reactive pause/activation, admitted active-order or tombstone changes; Viewer cannot issue it and server authorization is checked again. Other domain commands stay disabled until the human resolves or explicitly discards this retry option. Discard does not undo stored changes. Every deliberate new command then gets a fresh key and current command context; action kinds cannot resurrect historical failed closures. Dirty buffers remain on failures/CAS conflicts and are not cleared by acknowledgment of an earlier buffer after later edits. Opening the current version explicitly starts a new editing command. Workspace/account remounts and role epochs suppress stale acknowledgments; unmounts suppress late state writes. The editor uses native inputs/selects/time controls and existing UI primitives.

Public profile/history projections omit native job IDs, scheduling actor/connection approval, grant IDs and order command/actor/fingerprint internals. Current same-workspace immutable configuration and receipt references remain bounded and readable. History pages are limited to 25; UI requests ten at a time.
