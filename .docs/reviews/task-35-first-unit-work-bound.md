## Smallest useful backend strategy

Use a narrowly consumed **numerical-only original singleton text-post sample**, initially latest5 confirmed candidates/fixed24h observation age. The smaller candidate cap is a proposed structural UX limit, not a historical/data fact; label it explicitly. Text-only avoids media classification; one original position avoids claiming a complete publication inspector. Singleton/no-media is not an inherent limitation of numeric rights: it is the smallest first subset compatible with describe without media classification or full-thread coverage fanout. Text-only threads could follow using the existing complete-position logic; images would require current immutable media classification, and should not be silently labelled text. A media/thread/legacy-unprovable candidate contributes no number and no hidden omitted count.

Add a small concrete `readNumericSample` helper in the existing snapshots module (or an equally explicit reduced branch), reusing retainedSnapshotHorizon and describe. For each bounded candidate, validate exact account/workspace/version and singleton/no-media structure before consuming the24h snapshot. The new reader must propagate every unexpected error. Smallest safe first behavior is **no catch around retainedSnapshotHorizon**: if any admitted candidate's proof fails, the whole query is unavailable, with no numeric counts returned. This is conservative but truthful and needs no error registry. UI presents a finite generic unavailable code, never raw error bodies. A later partial-withdrawal contract would require distinguishing recognized proof losses from unexpected exceptions; do not bolt that onto this first unit. Existing horizon uses both plain Error(OWN_METRICS_SOURCE_UNAVAILABLE) and ConvexErrors, so the general `rethrowUnexpectedSourceError` allowlist is not a drop-in all-case classifier.

## Installed/current API evidence and precise limitation

Context7 official library resolution followed by docs ran outside sandbox (2 commands, no quota error). Sources: https://docs.convex.dev/api/interfaces/server.GenericQueryCtx and https://docs.convex.dev/database/writing-data . Installed source corroboration: convex/src/server/registration.ts:242–259 has QueryCtx.runQuery options transactionLimits and same read snapshot; meta.ts:20–45 defines used/remaining metrics and custom nested limits; impl/meta_impl.ts:13–25 exposes getTransactionMetrics; impl/registration_impl.ts passes limits to the native syscall.

Limits determine when a nested transaction **fails**, not a pre-read byte reservation. Official docs explicitly say consumed metrics include the overage of the document crossing the limit. Therefore do not claim that no operation can consume one byte beyond a configured cap. A post-success total metrics check prevents returning a success above the chosen ceiling; it does not undo reads already made. This distinction applies to the existing Health guard too, but this preparation is not reopening accepted Health.
