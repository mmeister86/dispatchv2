# TASK-33.1 first-unit YAGNI critique — READONLY proposal

Recommendation: first ship a **selected-workspace self-profile JSON download**, using one authenticated native query and the existing Cloud Settings mount. No exportJobs/exportChunks/exportSourceBindings, scheduler, storage, HTTP route, provider, Agent lookup or new index is needed for this finite scope. This is a useful partial export of the user's actual profile inputs (name, audience, topics, tone, timezone, language, onboarding), authenticated app identity and own current membership; it is explicitly not a whole account/workspace export or satisfaction of parent33/33.1 portability criteria.

## Output copies, unsupported scope and storage decision

The JSON response and browser Blob are **new physical copies** of allowed personal data. Do not persist them to native tables, Agent messages, provider logs, localStorage, R2 or app-owned browser caches. Keep only transient request/download state, dispose Blob URL after handoff, and clear pending response on scope loss. After saving, the user controls the local file; sign-out cannot erase that downloaded file. No bearer/signed URL or instant-revocation assertion is involved. Existing native row permission alone is not a blanket permission to materialize every descendant: the proposed contract authorizes only the declared self metadata DTO.

Unsupported, explicitly named without queried hidden counts: other actors/workspaces; whole shared workspace content; own private chats/Agent messages/tool payloads/streams/memories/files; Research and targeted chat; Ideas/routing/candidates/first/final verifiers and repair ancestry; plans/experiments/reviews; recipient notices and publishing mail receipts; publication attempts/unknown financial exposure/late effects; media original bytes; GitHub/source material; embeddings/style/performance; remaining Auth/component records and remote provider copies. There are no hidden-family cursors/counts/hasMore. No Admin private override. No global component enumeration. No deletion, source cancellation, refund, notification resend or finance normalization.

Durable jobs/chunks become justified only by an **approved concrete consumer** needing interrupt/resume or a large multipage own-chat/content archive. Then each produced protected chunk is itself a derivative: exact original actor/session/source dependencies and minimum horizons must be registered before readability, reproved on delivery, invalidated on source loss, and physically cleaned with bounded rootless hooks. `conversationAccess`/`historyAuthority` in `convex/ai/conversationAccess.ts` already enforce exact actor/account and source ancestry; a workspace Admin does not override them. Immutable job cutoff does not make multipage mutable reads a point-in-time snapshot. Such requirements explain the old jobs/chunks/bindings plan for the larger consumer, but are unnecessary for one synchronous metadata envelope. Do not create future fields now.
