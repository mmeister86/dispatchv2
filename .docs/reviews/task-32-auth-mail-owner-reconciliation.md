## Actual installation and producer distinction

Installed `@convex-dev/better-auth` is **0.12.5**; installed Better Auth itself is **1.6.33**, not0.12.5. Actual `convex/auth.ts` creates the default component client without local schema/triggers, and forwards only user.email and URL from both configured mail callbacks to its direct sendEmail. It does not capture the callback's token or request argument, command ID, original expiry, mail body digest, sequence or provider message ID. It checks response.ok only. App `auth.session` returns the **user** `_id`, not a session ID.

The callback producer bodies are materially different:

* Password reset (`better-auth/dist/api/routes/password.mjs:73–86`) creates a native verification value with original expiry and target user ID, then calls the configured sendResetPassword with `{user,url,token}` plus request. The raw-token-bearing identifier is framework-owned. The callback does **not** receive the native verification document ID, mail receipt ID or requester session. Reset can be requested without an authenticated session; its original recipient user is not a proven requesting actor. Nonexistent-user path deliberately returns a generic success response without sending.
* Reset completion consumes the verification row and updates password; configured revokeSessionsOnPasswordReset deletes sessions. Thus the original verification row can legitimately disappear before a late delivery callback. It is a consumable credential grant, not a durable original external-effect receipt. Keeping or rewriting it to retain mail evidence would alter authentication semantics.
* Email verification (`email-verification.mjs:13–35`) generates a signed JWT and passes `{user,url,token}` plus request. This producer does **not** create a native verification table row for that token. Inspected sign-up and unverified sign-in producers use the same JWT callback pattern, before the new successful session is created. A verification table on the component schema does not imply a verification-row parent for this email flow. Existing sign-up/sign-in/session facts are not one mail occurrence.

Only static source patterns were read. No actual URL, token, email, session cookie or provider response was obtained, decoded or queried. These observations do not propose overriding JWT/token creation, consuming a token to record delivery or authenticating via a provider callback.

## Smallest viable proposed owner and admission

A whole generic app notification journal is unnecessary. If Root releases Auth delivery tracking, the demonstrated absent owner justifies **one finite auth-mail receipt family** outside the component, owned by the two existing Auth send callbacks. Existing app users/preferences are unsuitable storage: an unverified sign-up may not yet have an app user/workspace, and concurrent security requests cannot be safely overwritten on one mutable user/session field. Requested auth mail is not an AI financial ledger or workspace optional digest.

Proposed bounded auth-specific row, not installed schema/API: kind=`verification|password_reset`; original BetterAuth target user ID; original normalized-recipient fingerprint; immutable opaque request identity/body digest/config binding; original createdAt/notAfter; sequence/claim/lease; send state=`configuration_required|sending|provider_accepted|known_rejected|unknown|suppressed`; provider message identity if genuinely observed; finite signed event/replay/ordering evidence; terminal sourceUnavailable and indexed cleanAfter. Optional requester-session evidence is null unless actually established by that original request; it is never the target user's current session assumed retrospectively. No workspaceId/draftId is forged. No raw URL/token/body/email is returned in public DTOs or technical logs.

Native original request identity must come from the **trusted configured callback invocation**, not client-selected email/user/request ID. Capturing a bounded digest of the original high-entropy credential/request bytes internally is a possible dedupe binding, subject to future security/source review; it is not a current API assertion or reason to persist raw credentials. New original credential bytes are a distinct requested occurrence; a repeated identical callback intent cannot rotate key/body/expiry or create another attempt. A mail digest/idempotency fence cannot replace the framework's actual verification/reset token validity checks.

Claim and record before POST; same original request and finite horizon govern all explicit repeats. Proposed minimum policy is one automatic physical request per original callback, no background resend after unknown. The original URL can remain in that in-memory callback only for this first send; durable receipt stores evidence hashes/IDs, not a replayable auth URL. Explicit durable resend of identical secret bytes would require a separately approved protected-copy retention/encryption and original-expiry solution; do not claim it works from hashes alone. Prefer a new explicit framework request with a genuinely new credential over reconstructing or reviving a consumed credential. This is a policy proposal, not auth redesign or token issue API usage.

Reprove the actual target auth user/current email and original credential horizon immediately before admission, using source mechanisms reconciled at implementation. Reset's original verification expiry can corroborate admission while the native row still exists; JWT's original framework expiry must be captured from the trusted producer contract without inventing a verification row or arbitrary fresh window. Do not merely assume the framework's default one-hour value, decode an untrusted client token as authorization, or renew expiry when mail retries. Bounds must be min(original credential horizon, firstSendAt+finite mail window). Missing configuration/expired recipient/source yields zero send and a safe visible result. Whether a mail failure should surface synchronously versus preserve the framework's generic anti-enumeration response requires exact existing endpoint semantics; don't expose recipient existence/provider state to anonymous callers.

A signed mail provider callback binds the **original row and provider message identity** and may append genuine late external evidence after auth token consumption/session revocation/user erasure. It cannot verify an email, issue a session, reset a password, extend token expiry or recreate a user. Lost HTTP ACK with no stored provider ID remains unknown/unbound unless an officially documented original correlation mechanism is implemented and tested; no matching by recipient/time alone. Original signed recipient/body-replay/sequence/order checks remain exactly the separate32proposal obligations.
