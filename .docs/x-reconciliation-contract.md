It does not infer absence from missing provider results. Snapshots, approved historical media/alt and real external IDs/links remain visible. The human Owner/Admin supplies a numeric 1–19 digit candidate ID or a narrowly parsed canonical HTTPS `x.com/<handle>/status/<id>` or `x.com/i/web/status/<id>` link without userinfo, port, query or fragment. The client input is only a lookup argument. Only the fixed official `GET https://api.x.com/2/tweets/{id}` endpoint is requested, redirects are rejected, the streamed body is capped at 32 KiB, and the read times out at 15 seconds. No supplied link, entity URL or arbitrary origin is fetched.

A separate concrete internal Node `integrations/x/client.credentialForReconciliation` reuses native encrypted-token opening. The ordinary publishing token path retains all its send guards. Paused reads authorize the current verified session, active selected workspace/lifecycle and current Owner/Admin, same stored immutable version/account/provider identity, reciprocal binding, current connected account, current credential generation, no refresh lease, >30 seconds token validity, users.read/tweet.read, exact read sequence and lease. Same-identity reconnect may supply current readable credentials without reviving old publishing authorization. Different identity fails. Authorization, connection and credential/read sequences are checked again before GET and when committing evidence. The existing concrete first-write media source block is reused separately: immutable ordered asset/checksum/object pins, current workspace references, ready R2 asset/session association, SHA shape, final namespace, size/MIME and configured bucket/account binding are checked on every read source and evidence commit. A provider media key does not prove the original R2 SHA. Paused reads do not call the whole publishing preflight or require an unexpired old write intent.

A positive match requires actual returned requested ID and author, a single unedited `edit_history_post_ids=[id]`, full exact approved text under NFC comparison only, exact expected confirmed reply parent in `referenced_posts`, actual `attachments.media_keys` matching captured upload keys, and a RFC 3339 creation timestamp between recorded request start minus 5 seconds and plus 60 seconds. No other reference is accepted. Captured missing media keys do not become inferred keys. For transformed URLs, the installed twitter-text URL parser must identify the complete approved expanded URL and one actual returned t.co token. A conservative whitespace/end boundary excludes the parser's t.co suffix truncation; adjacent punctuation or unsupported tokens remain unknown. Bounded literal substitutions are accepted only when each complete-token mapping is unique and unambiguous. Entity index units are not guessed, no fuzzy/trimmed comparison is used, and approved content is never rewritten. Unsupported note content, edits, fields or mappings remain unknown.

GET 404, missing/protected/deleted/edited posts, empty data, wrong author/text/ID/parent/media/time, transport failures and timeouts never turn an unknown write into unsent. Successful lookup only records actual confirmed evidence and its canonical X link, with an internal exact attempt/position/version/provider/generation/read-sequence/current-credential CAS. A different confirmed ID cannot replace the first. Repeated confirmation is idempotent. An explicit fresh Owner/Admin lookup after the window may authorize another bounded window; the monotonic read sequence and unknown outcome remain. Provider not-before is still honored, including hints beyond the current window. A crashed read cannot grant proof; its lease expires without converting the write to absent. UI shows backoff and wakes its disabled controls when the persisted time arrives.

## Explicit continuation

`continueThread` is a current human Owner/Admin CAS against the exact displayed schedule generation. It requires a resolved confirmed prefix, matching actual attempt references/version/account/provider identity/position/IDs, no historical sending/unknown effect, no persisted abort, current readable/write scope/connection/binding, valid immutable source/media checks, and the same stored version. It does not replace content with the current working draft, change media/alt, or treat risk acknowledgement as proof of absence.

A definitely rejected 429 may continue only after actual Retry-After/reset.400/422 are permanent content rejections and require a new separately approved operation rather than repeating that snapshot.401/403 require restored access; preparation failures can continue only after current source/approval/media guards pass. Possible POST effect failures remain unknown, including 5 xx and timeouts; no blind retry exists.

The separate visible acknowledgement reauthorizes that exact immutable version/account, creates a current human approval with the same historical media placement, pins the current connection and gives it a 45 minute publishing intent. If the current connection's write capability is unverified, the concrete command persists `first_write_verification`, including an originally ordinary partial job after same-identity reconnect. This is an explicit visible write verification for only remaining positions; normal calendar approval/scheduling cannot invoke a general bypass. Only a later actual current credentialed 201 numeric-ID POST acknowledgement proves capability. Different identity/content requires another operation.

Generation increments once. The existing `attempts.claim` reads and validates the retained `externalPosts` prefix across generations and selects only its first missing position; the parent is the last actual confirmed ID. It validates provider identity across bounded history and rejects historical unknown/sending effects. Old scheduled calls cannot claim the new generation. Media remains first-post-only and actual previous upload evidence remains historical. Before an unsent first position the existing bounded media engine prepares expired IDs under the approved source/alt guards. Confirmed positions are immutable and never uploaded or sent again.

Persisted `abortRequestedAt/By` are never cleared. Positive reconciliation may retain confirmed links and finalize an abort as cancelled when all possible effects are resolved. An authorized idempotent lookup against an already confirmed late receipt may finalize the same abort without another GET. Outstanding sending/unknown evidence preserves the account barrier; cancellation/deletion/connection loss cannot produce write capability or continuation. External deletion remains a separate operation, never rollback.
