## Mapping and actual history

Two concrete stores are added: `conversations` maps current workspace/account/actor to one actual official Agent thread; `chatOperations` binds each stable send key to one saved native prompt, immutable selected idea version, bounded continuation run IDs and one actual idea receipt/fingerprint. There is no second messages/history table, embedding model, cross-thread search, generic AI router or client-selected component thread/model/user. Conversations are personal within the workspace/account; the component's shared userId is not authority.

Every public read/title/send/stop/resume/delete binds the current authenticated workspace, account and original actor before component I/O. Current workspace lifecycle, role for writes and actual referenced objects are checked. Thread IDs accepted by the native UI hook are domain conversation IDs, normalized and resolved server-side; raw component IDs are never adopted. History/stream projection also checks every admitted source's actual immutable version, current repository purposes/generation/proof, context hash approval and captured credential/actor constraints. Withdrawn or unproved private history produces an empty native projection before message/delta reads. Safe financial/provenance receipts remain available. The UI consumes a minimal authorization/proof-deadline projection through the existing GitHub deadline-clock hook and explicitly hides cached native messages when expired or revoked.

Native Agent0.6.4 `listDeltas` does not validate cursor ownership using its threadId argument. This wrapper validates at most100 unique cursors, safe nonnegative integer positions and list start order, proves each ID through actual native thread-indexed `listStreams` including streaming/finished/aborted, then reads only proved IDs. Unproved/older/deleted/foreign IDs are omitted, never probed. The native metadata window is100; older streams resync through paginated official history. Authorized history permits the hook's zero-item stream-only sentinel and up to50 real messages per page. The UI initially loads20, supports older-page loading and shows the last25 personal conversations with that limit labelled. Conversations accept50 sends, ten immutable source versions and five run incarnations per operation; these are explicit finite ceilings, not invented completion percentages.

## Funding and continuation

Chat requires a new explicit `chat` purpose in the current policy and all three scoped budget grants. Existing draft processing permission does not activate chat. No policy/grant is seeded. The reviewed fixed Requesty EU endpoint, mandatory current Owner/Admin grant approvers, configuration fingerprint, exact account connection sequence, byte/token/attempt/tool/deadline limits, pre-physical-request reservation, retry0/no fallback and independently settleable late usage remain intact.

A send saves one native prompt, operation mapping and run in one transaction. Contradictory repeated keys fail; exact retries return the actual initial run and never resave the prompt. Current source bindings are conservatively retained for the whole conversation, not just the newest send; a source-less prompt cannot resend previously revoked private history to the model. Start a new conversation instead of introducing a history-redaction engine.

Stop commits the domain generation fence before scheduling bounded native abort. Scheduled abort is tied to the actual stopped run and cannot abort a newer continuation. Explicit resume creates a new currently covered run using the same saved prompt; stopped authority is not reopened and completed content receipts are retained. Installed Agent0.6.4 `fetchContextWithPrompt` uses native `listMessagesByThreadId` with the saved prompt ID; the component includes successful responses at the same message order. There is no claimed native same-order cutoff. A domain idea write can nevertheless complete before the SDK persists its tool response or stop interrupts execution. The currently authorized operation receipt is therefore passed explicitly in continuation instructions, and `create_idea` is omitted once this operation already has an actual result (and whenever human permission is absent). No input message is duplicated. Any sent/unknown attempt of that same operation blocks resume and every later physical call of a continuation; a fresh run ID is not a financial reset. Each incarnation has its own displayed currency/token/estimate/hold receipt, with no cross-currency totals or fabricated billed amount. A distinct explicit send is new work requiring actual coverage and does not erase previous liability.
